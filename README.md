# Club Pass — QR-пропуска и баллы мероприятий

Сервис регистрации гостей мероприятий бизнес-клуба с персональными QR-пропусками, проверкой посещений и журналом начисления баллов.

## Возможности

- Гость регистрируется в боте (`/register`), выбирает категорию и получает QR (`/qr`).
- Организатор присылает боту фотографию, пересланное изображение или файл с QR. Если картинка не читается, можно вставить текст из QR.
- Бот показывает карточку: имя, категория, сумма баллов и статус прихода.
- «Отметить приход» добавляет баллы **ровно один раз**. Дополнительные баллы можно выдать кнопками +5/+10/+20 или указать произвольные сумму и причину.
- Каждый факт начисления хранится отдельно: сколько баллов, за что, когда и ID организатора. Гость видит последние начисления через `/history`.
- Организатор определяется по разрешённым Telegram ID. Обычный гость не может читать карточки других гостей или начислять баллы.

## Стек и архитектура

Python 3.12, FastAPI, aiogram 3, PostgreSQL, SQLAlchemy 2 (async), Alembic, OpenCV, qrcode, Docker Compose, pytest.

```text
Telegram  ──> aiogram-бот  ──> HTTP (внутренняя сеть Docker) ──> FastAPI
                                                               │
                                                               ▼
                                                           PostgreSQL
```

Бот отвечает только за интерфейс, скачивание/распознавание изображений и кнопки. Правила безопасности, регистрации, прихода и начисления находятся в backend. Данные хранятся в PostgreSQL. Схема БД меняется миграциями Alembic.

Структура:

```text
app/
  api.py           защищённые HTTP endpoints
  service.py       бизнес-операции
  models.py        таблицы базы данных
  schemas.py       проверка входных данных и ответы API
  security.py      подпись QR-пропуска (HMAC-SHA256)
  qr.py            создание PNG и декодирование QR-фото
  database.py      асинхронное подключение к БД
  config.py        переменные окружения и их проверка
  bot/
    handlers.py    Telegram-команды, сообщения и кнопки
    client.py      HTTP-клиент к backend
    main.py        запуск Telegram long polling
alembic/           миграции
tests/             unit- и интеграционные тесты
compose.yaml       запуск API, бота и PostgreSQL
```

## Запуск на macOS / Linux

**Нужно:** Docker Desktop (Docker Compose v2), Telegram и хотя бы один Telegram-аккаунт для тестирования. Второй аккаунт удобен для проверки роли организатора.

1. Создайте бота через [@BotFather](https://t.me/BotFather): `/newbot`. Сохраните полученный `BOT_TOKEN`.
2. Узнайте свой числовой Telegram ID (например, у [@userinfobot](https://t.me/userinfobot)). Если хотите несколько организаторов, перечислите их ID через запятую.
3. Скопируйте файл с настройками:
   ```bash
   cp .env.example .env
   ```
4. Сгенерируйте **два разных** случайных ключа. Эту команду запустите дважды:
   ```bash
   python3 -c 'import secrets; print(secrets.token_hex(32))'
   ```
5. Откройте `.env` и заполните `BOT_TOKEN`, `SIGNING_KEY`, `INTERNAL_API_KEY`, `ORGANIZER_IDS`, `POSTGRES_PASSWORD`. В пароле БД используйте буквы/цифры, чтобы не пришлось URL-кодировать специальные символы. Для демо `CHECKIN_POINTS=10`. Файл `.env` **не загружайте в GitHub**.
6. Запустите в папке проекта:
   ```bash
   docker compose up --build -d
   ```
   Docker поднимет PostgreSQL, выполнит миграцию, запустит FastAPI и Telegram-бота. Это одна команда; миграции отдельно делать не нужно.
7. Проверьте состояние:
   ```bash
   docker compose ps
   docker compose logs -f bot
   ```
   В браузере можно открыть <http://localhost:8000/docs> (API-документация) или <http://localhost:8000/health> (состояние БД).
8. Откройте бота в Telegram, отправьте `/start` с аккаунта **обычного гостя**, затем `/register`, введите имя и категорию. Бот вернёт QR-картинку.
9. С аккаунта организатора (ID указан в `.env`) отправьте `/start`, затем фотографию QR гостя. Нажмите «Отметить приход»: статус и баллы обновятся. Нажмите повторно — повторных баллов не будет. Дополнительные начисления работают отдельно.
10. Для остановки:
    ```bash
    docker compose down
    ```
    Данные останутся в Docker volume. `docker compose down -v` **удаляет данные**, используйте только если хотите сбросить БД.

Если изменили `.env`, перезапустите: `docker compose up -d --force-recreate`. Для нового кода: `docker compose up --build -d`.

## Как устроен пропуск и почему его нельзя подобрать

В QR записана строка вида `bc1.<случайный nonce>.<HMAC>`. `nonce` — 24 криптографически случайных байта в base64url, не ID гостя. HMAC-SHA256 вычислен с приватным `SIGNING_KEY`, который хранится только на backend. При запросе сервер сначала проверяет подпись (`hmac.compare_digest`), затем ищет `nonce` в таблице гостей. Подмена, подбор числового ID и добавление собственного QR не работают. **Сам QR является пропуском на предъявителя:** пересланную реальную картинку технически можно использовать, поэтому на входе организатор видит имя для сверки; при необходимости можно добавить проверку документа или ротацию пропусков.

Отметка прихода: `checkins.guest_id` — первичный ключ. Операция `INSERT ... ON CONFLICT DO NOTHING RETURNING ...` решает проблему гонок даже при двух сканированиях одновременно. Баллы за вход записываются в `point_events` **в той же транзакции**. Повторная отметка не создаёт ни второй вход, ни второе начисление. Бонусы — отдельные записи с пояснением. Итог — сумма записей журнала, а не редактируемый счётчик.

Примечание: бонусы разрешены повторно, поскольку это **отдельные награды**, не чек-ин. Если событие не должно допускать повторного бонуса, потребуется дополнительный уникальный идентификатор награждения. Также каждый `SIGNING_KEY` должен оставаться неизменным для уже выданных пропусков: его замена делает старые QR недействительными.

## API

Внутренние endpoint'ы защищены заголовком `Authorization: Bearer <INTERNAL_API_KEY>`. Во всех endpoint'ах организатора дополнительно проверяется `organizer_id` по серверному белому списку `ORGANIZER_IDS`. API слушает локальный порт 8000, для интернета его открывать не нужно.

| Метод | Endpoint | Назначение |
|---|---|---|
| `GET` | `/health` | Проверка доступности базы |
| `POST` | `/api/v1/guests` | Регистрация гостя |
| `GET` | `/api/v1/guests/by-telegram/{id}` | Получить QR гостя |
| `GET` | `/api/v1/guests/by-telegram/{id}/history` | История начислений с пагинацией |
| `POST` | `/api/v1/organizer/lookup` | Найти гостя по подписанному QR |
| `GET` | `/api/v1/organizer/guests/{id}` | Обновить карточку |
| `POST` | `/api/v1/organizer/checkin` | Однократная отметка входа |
| `POST` | `/api/v1/organizer/bonus` | Начислить дополнительные баллы |

Важное ограничение: API намеренно **внутренний, с единым сервисным ключом**, не публичный пользовательский API. Telegram ID проверяется ботом по реальному Telegram update, а не принимается от произвольного клиента из интернета. Для открытия API внешним приложениям понадобится отдельная схема авторизации пользователей (OAuth/JWT с ролями), HTTPS и rate limiting.

## Проверка

Запустить unit- и интеграционные тесты через отдельную тестовую БД:

```bash
docker compose --profile test run --build --rm tests
```

После тестов можно остановить только тестовую базу: `docker compose --profile test stop test-db`. Основную базу и данные приложения это не затронет. Проверка гонки одновременно имитирует три запроса на один и тот же QR и подтверждает однократное начисление.

Локально, если Python и зависимости уже установлены:

```bash
python3 -m pip install -e '.[dev]'
ruff check .
pytest -q
```

Без `TEST_DATABASE_URL` интеграционные тесты пропускаются, но unit-тесты выполняются.

## Решения и ограничения

- Категории гостей для демо фиксированные (`Гость`, `VIP`, `Спикер`), их список можно вынести в таблицу БД.
- Самостоятельная регистрация упрощает тестирование. Для закрытого мероприятия её нужно ограничить предварительно утверждённым списком гостей.
- QR остаётся постоянным для гостя в рамках демо. При необходимости можно добавить срок действия и отзыв/переиздание пропуска.
- Бот работает через polling — так не нужен публичный HTTPS и можно запустить проект локально одной командой. Для production лучше webhook и мониторинг ошибок.
- Для безопасности данные о гостях и журнал событий не логируются. У Telegram всё равно есть копии пересылаемых изображений: учитывайте политику обработки персональных данных.

## Использование ИИ

В ходе разработки использовался ChatGPT для проработки структуры приложения, генерации первоначальных версий отдельных модулей, API-обработчиков, миграций, тестов и документации.

Ключевые технические решения и их обоснование:

- **Подписанный случайный токен вместо открытого ID:** QR содержит случайный идентификатор и HMAC-SHA256, чтобы нельзя было получить чужой пропуск, просто подставив число.
- **Уникальность посещения на уровне PostgreSQL:** вариант с проверкой флага и последующим начислением не подходит из-за возможных параллельных запросов. Используется ограничение уникальности и `INSERT ... ON CONFLICT DO NOTHING` с начислением в одной транзакции.
- **Готовая библиотека распознавания:** для извлечения QR из фотографии выбран OpenCV вместо собственной реализации декодера.
- **Разделение ответственности:** Telegram-бот обрабатывает сообщения, а валидация пропусков и операции с баллами выполняются в backend.

Unit-тесты покрывают подпись и проверку токена, QR и валидацию схем. Интеграционные тесты проверяют операции с PostgreSQL, включая конкурентные отметки посещения. Тесты запускаются командами из раздела «Проверка»; для интеграционных сценариев требуется отдельная тестовая база. Работа с реальным Telegram API и Docker Compose требует настроенных переменных окружения.
